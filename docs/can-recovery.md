# CAN 故障恢复与重新使能

CAN1/2 的波特率和 CubeMX 文件保持原值，未启用 RTOS。恢复由主循环调用的
`BspCan_Service()` 执行，不在接收中断里等待，不修改电机 ID 或电调参数。

消息中心每次最多派发 64 条消息，即使 CAN 持续涌入，也会执行发送刷新并返回主循环，
避免旧版“等队列完全空了才返回”使恢复和控制任务长期得不到运行。诊断可读取派发次数、
处理消息数、达到批次上限次数和队列覆盖数。

## 故障时的行为

任一路检测到 Bus-Off 后，两路电机输出都锁定。先请求取消两路硬件邮箱中的旧报文，
并将 DJI 软件发送缓冲中的控制值清零。必须确认故障通道的邮箱全部空闲，才请求进入
CAN 初始化模式；收到 INAK 后清除 INRQ，等待硬件完成总线同步及 BOFF 清除。
任一步超时都会保持停机，至少等待 1 秒后重试。恢复不能修好松动的接头、异常供电或
错误终端电阻；如果物理故障持续，控制器可能再次进入 Bus-Off。

主循环持续发布停机命令。云台清除旧目标及 PID 状态；摩擦轮和拨弹立即清零，
不以旧速度目标做减速斜坡。CAN 恢复期间不会执行积压的非零指令。

2026-09-09 按用户要求恢复摩擦轮原先的正常下档逻辑：在 CAN 已解锁、反馈有效时，
下档将目标按每次命令回调 500 RPM 逐步降至零，速度 PID 继续工作以制动及维持零速。
这与故障停机不同：CAN 故障锁定仍立即清目标/PID并输出零电流，反馈超时也不执行制动。
原运行目标 ±7500 RPM、PID 参数、上电回下档保护和拨弹逻辑保持当前设置。

## 上电或恢复后

1. 确认装置可安全运动，两只遥控拨杆均放下位，五个模拟通道回中。
2. 两路 CAN 无 Bus-Off、错误被动或错误警告并保持至少 500 ms 后，遥控在线且上述
   安全位置再持续至少 500 ms，才解除输出锁定。
3. 解锁当次仍发送停机命令。云台反馈还需连续新鲜至少 100 ms，随后将当前角度作为
   保持目标。任一云台轴反馈超过 100 ms 未更新，会使两轴输出清零、清 PID 并重新对齐。
4. 摩擦轮在启动或遥控断线后，必须先收到发射拨杆下位，再切到中/上位才允许运行。
   中位运行摩擦轮，上位同时运行拨弹。没有改变运行转速或 CAN 控制协议。

当前停机是软件控制措施，不能代替切断动力。调试烧录仍保留“不自动运行”的本机设置。
请在下载完成且机械区域安全后再人工 RESET；不要为验证 Bus-Off 主动短接 CAN 线。

## 诊断及验证边界

`BspCan_GetRecovery()` 可读取两路的阶段、故障次数、恢复次数、超时次数、最近一次
进入故障时的 ESR 和最近非零 LEC 的 ESR。阶段 0/1/2/3/4/5 分别是就绪、取消邮箱、
等待初始化、退出初始化、等待同步、等待重试。LEC 由主循环采样，可能漏掉很短的错误，
不能代替总线分析仪的完整记录。

CAN 管理器的 `tx_ok` 是提交到邮箱成功次数，不是已被电机确认的次数。
接收回调增长只能证明收到数据，不能单独证明控制指令成功发送。

主机测试使用真实 BSP 状态机及应用回调，模拟邮箱取消、初始化握手、持续故障、恢复
等待、回中解锁、云台掉线重连及摩擦轮停机；它们不模拟模拟电气特性或证明机械运动安全。
实机是否已恢复必须以新固件运行后的寄存器和反馈记录为准。

2026-09-09 实测：最终固件已下载校验并人工 RESET。两次读取中 CAN1 故障/恢复次数
从 45/45 增至 94/94，恢复超时为 0；主循环及两路发送提交计数持续增长，CAN2 错误为 0。
这证明恢复和派发流程在运行，但 CAN1 仍反复出现新故障，初始电气原因尚未排除。
保护保持未解锁，底盘及摩擦轮输出为零。消息队列仍有大量覆盖，吞吐和机械控制性能
不能据此宣称已验证。详见项目记忆与 `build/can-final-a/b.log`、对应 JSON 快照。
